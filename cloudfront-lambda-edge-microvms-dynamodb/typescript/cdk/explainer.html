One CloudFront URL, one Lambda MicroVM per session

Every session gets its own AWS Lambda MicroVM behind a single Amazon CloudFront URL. The session id in the path (/s/{id}/…) or query string (?session={id}) picks the VM; a Lambda@Edge function routes to it, and a control-plane Lambda launches it the first time.

Core ideas

  • DynamoDB maps session id to MicroVM. One table, one record per session: microvmId, endpoint, token and when the token expires. Records expire after 24 hours.
  • The edge function routes. On every request it reads the record. A valid token means proxy to the VM (origin, Host header, auth token, port 8080). Anything else means a 307 to /_control, or a 503 if the control plane already ran once. Session ids must match ^[A-Za-z0-9_-]{1,64}$ or get a 400.
  • The control plane launches on demand. It attaches to a live VM or starts one, mints a 30-minute token, stores it, and redirects back. A conditional write claims the launch, so two simultaneous first requests start one VM, not two; the loser gets a 503 and succeeds on retry.
  • Idle VMs suspend, resume, then terminate. After 15 idle minutes a VM is suspended; the next proxied request resumes it. After 30 more suspended minutes it is terminated, and the next request launches a fresh one.
  • Lambda@Edge has no environment variables, so the table name and Region ride as custom headers on the CloudFront origin.

Is it a fit?

Good fit

  • Each user or session needs its own isolated process, filesystem and memory.
  • Sessions are stateful and live for minutes to hours.
  • The first request can tolerate a redirect and a cold launch of up to ~20 seconds.
  • Your app uses relative asset paths, so stripping /s/{id} is harmless.

Not a fit

  • Stateless request handling: a plain Lambda function or container is simpler.
  • You can't deploy in us-east-1; Lambda@Edge requires it, and far-away viewers pay a round trip to the single-Region table.
  • Your app references assets by absolute path (/assets/…); route by subdomain instead.
  • Untrusted users without adding authentication first.

For production, add authentication first: as shipped, anyone who knows a session id reaches that VM. Then consider a DynamoDB global table for lookup latency and subdomain routing if your paths are absolute.
